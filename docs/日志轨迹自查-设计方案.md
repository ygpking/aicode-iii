# 设计方案：让 AiCode 能自查日志与轨迹

> 目标：打通「AiCode 产生的日志/轨迹 → AiCode 自己读取分析 → 改进修复能力与提示词」这条链路。
> 本文只做设计，**不含已实施的代码改动**；标注为「需改动」的部分等你确认后再动。

## 一、现状（已核实）

| 事实 | 位置 |
| --- | --- |
| 日志/轨迹写在**宿主侧**外部私有目录 | `FileLogger`/`AILogger`/`EventTrace` 均用 `context.getExternalFilesDir(null)`，即 `/storage/emulated/0/Android/data/com.aicode.iii/files/` 下的 `logs/`（FileLogger:88）、`ai-logs/`（AILogger:55）、`traces/`（EventTrace:97） |
| 容器挂载了 `/root/.aicode`（**读写**）、`$projectPath:/root/workspace` | `LinuxContainerEngine.buildBaseProotArgv()`（:827 起） |
| **未挂载** `files/` 目录 | 挂载列表只有 `/dev /proc /sys /system` + workspace + `.aicode` |
| 结论 | **AI 在容器内物理上读不到自己的日志/轨迹** |

另：`EventTrace` 的消费方目前只有 `StorageUsageScanner`（读 `totalBytes` 做占用统计）与清空，
没有任何「读取 → 分析」的环节。`prompts/` 是静态资产，由 `ContainerInstaller` 单向复制到
`/root/.aicode/prompts/`，无回写通道。

## 二、方案：只读挂载 + 分析脚本（最小改动、无污染）

### 2.1 挂载改法（需改动）

**要改的是内置 profile，而不是用户的配置项。**
核实：`ContainerProfile.BUILTIN_ALPINE`（`ContainerProfile.kt:49`）的 `extraBindings` 目前是
**默认空**（`extraBindings: List<String> = emptyList()`，:24）。所以「让内置容器也能自查」
必须在内置 profile 上补绑定，用户自建 profile 则各按需要。

绑定格式（与现有 `-b <binding>` 拼接一致，`:864-867`）：

```
<宿主源绝对路径>:<容器目标路径>
```

建议新增两条：

| 宿主源 | 容器目标 | 说明 |
| --- | --- | --- |
| `<files>/traces` | `/root/.aicode/traces-view` | 事件轨迹 |
| `<files>/logs` | `/root/.aicode/logs-view` | 应用日志 |
| `<files>/ai-logs` | `/root/.aicode/ai-logs-view` | 模型请求原文（含脱敏后的内容） |

实现要点（基于本仓库已有的两条硬约束）：

1. **必须走 `profile.extraBindings` 而非硬编码 argv**。
   `ContainerProfile` 的注释记录了反面教训：硬编码 argv 的位置与手动添加不同，会导致
   `--link2symlink` 行为异常且无法在编辑页撤销。故新增绑定应拼进 `extraBindings`，
   与现有机制走同一条路径。
   额外好处：`extraBindings` 会被 `WorkspacePathMapper`（:156 `extraMounts()`）解析成路径映射，
   使**工具层**（readFile/list/search）也能正确识别这些路径；硬编码进 argv 则拿不到这个联动，
   工具层会把容器路径兜底落到 rootfs 内部，与 shell 看到的不一致。

2. **proot 的 `-b` 要求源路径存在**（`buildBaseProotArgv` 注释明确写了）。
   日志目录是**惰性创建**的（`FileLogger.init` / `EventTrace.init` 才 `mkdirs()`），
   若容器先于首次写日志启动，源路径不存在会导致挂载失败。
   **必须在挂载前主动 `mkdirs()`**，与 `.aicode` 挂载同样的处理。
   （`FileLogger.kt:89`、`AILogger.kt:56`、`EventTrace.kt:97` 三处 `File(base, ...)` 均可
   在 `init` 时顺带建立，或由容器启动前统一 ensure。）

3. **只读性（需实测确认）**：PRoot 的 `-b` 官方约定是 `src:dst`，**未见到 `:ro` 后缀的用法，
   本仓库也没有先例**（全仓 `rg ':ro'` 无命中）。因此「只读」**不能假设挂载标志能实现**，需按：
   - **首选做法**：挂到 `/root/.aicode/traces-view/` 这种**带语义的只读视图名**，
     降低 AI 误写的概率；并在 `prompts/` 中明确该目录是证据、禁止写入。
   - **不要指望文件系统权限**：PRoot 是伪 root（`-0`），chmod 对宿主是模拟的，**拦不住写入**。
   - **兜底**：`scripts/analyze_traces.py` 本身只读（已实测 md5 无损），分析环节不会改数据。

   > 待你确认的点：若实测发现 PRoot 确实支持 `:ro`，则优先用挂载标志做**真实**隔离；
   > 本方案当前按「无法强制隔离」设计，故用命名语义 + 提示词约束 + 脚本只读三重降低风险，
   > 而不声称有强制保护。

4. **挂载目标不要与 `.aicode` 现有子目录冲突**。
   现有挂载是 `-b <aicodeDir>:/root/.aicode`（读写），其中已含 `skills/`、`prompts/`。
   新增的 `*-view` 是它的**同级子目录**，proot 支持嵌套绑定（更具体的路径优先生效），
   但为避免歧义，命名统一加 `-view` 后缀，明确「这是只读视图」而非可写数据区。


### 2.2 为什么不直接挂整个 `files/`

`files/` 下还有 `databases/`、`shared_prefs/` 等**可能含敏感信息**的目录，且是 App 的私有数据。
只挂 `logs/` 与 `traces/`（且是只读视图）能把暴露面压到最小。这与 `45-security` 的
「不把凭据传给会外发的工具」精神一致。

### 2.3 分析脚本

已交付两个**只读**脚本（本轮已实现并实测）：

| 脚本 | 作用 |
| --- | --- |
| `scripts/analyze_traces.py` | 把轨迹聚合成跨回合结论：错误码频次、未收尾回合、`TRACE_DROPPED`、收尾残留快照、进程生命周期 |
| `scripts/audit_error_codes.py` | 从源码提取 code 全集，对账文档覆盖度、检测同义分裂 |

**两者可串联**，解决「分析脚本的白名单滞后于代码」这一必然发生的漂移：

```bash
# 1. 从源码导出最新码全集
python3 scripts/audit_error_codes.py --emit-codes --out /tmp/codes.txt

# 2. 用最新白名单分析轨迹（否则新码会被当成「未知词」）
python3 scripts/analyze_traces.py --dir <traces> --codes-file /tmp/codes.txt
```

`analyze_traces.py` 的错误码识别用**白名单**而非黑名单：白名单外的大写词会**单独列出**而非
静默丢弃——它们要么是代码新增的码（白名单该更新），要么是噪声（黑名单该更新），两种都需人看见。
内置快照（130 个）可能滞后，报告首行会标明当前用的是哪套白名单。

挂载打通前后都能用：

- 打通前：开发者/用户在宿主侧直接跑（`--dir` 指向 `Android/data/.../files/traces`）；
- 打通后：AI 在容器内
  `python3 /root/.aicode/scripts/analyze_traces.py --dir /root/.aicode/traces-view`。
  （前提：`scripts/` 需随 `ContainerInstaller` 释放到容器，见 P2 待办。）

## 三、防污染设计（自动化前必须解决）

若将来要做「轨迹 → 教训 → 提示词」的**自动**闭环，以下四点必须先设计掉：

### ① 轨迹自我污染（最高危）

若 AI 读取轨迹的过程本身产生轨迹，就会污染下一次分析。`AILogger` 已有先例：其 `write()`
对 detail 做了 `MediaRedactor.redact`，说明团队已意识到「日志内容本身要净化」。

**要求**：读取/分析轨迹的动作**不得写入轨迹**。可行做法：
- 分析脚本不调任何 App 内 API（已满足：纯 Python + 文件读取）；
- 若将来做成工具，该工具须标记为「不记录轨迹」。

### ② 提示词「覆盖 vs 追加」的语义陷阱

`PromptFragmentResolver` 的规则是：**数字命中内置片段 = 覆盖**（见该文件 KDoc：「数字即身份。
数字命中内置静态片段即为覆盖，否则作为新增片段并入静态基线按数字排序」）。
自动生成的教训若写进 `03-xxx.md`，会**静默顶掉**内置片段。

**要求**：自动写入必须走「新增数字」或独立通道，并在写入前检查数字是否已占用；
绝不允许直接覆写既有编号。

### ③ 无界累积

`EventTrace` 有 `MAX_RECORDS_PER_TURN` / `MAX_FILE_BYTES` / `MAX_AGE_DAYS` 三重上限，
**这是对的**。但提示词**没有上限机制**——而 prompt 是每轮都进上下文的固定开销，
无限追加会加剧上下文压力（正是本轮在修的那类问题）。

**要求**：教训条目设上限 + 过期/合并机制，且要能回答「这条什么时候该删」。

### ④ 来源可追溯

`EventTrace` 的哲学是**每条记录可倒推来源**（`causeSeq` + 显式说明未收尾回合，不掩盖不确定性）。

**要求**：每条从轨迹提炼的教训必须能**回指**：哪个会话、哪个回合、哪条 `seq`。
否则无法判断它是稳定模式还是孤例、是否已过期。

## 四、执行顺序建议

| 阶段 | 动作 | 风险 |
| --- | --- | --- |
| P0（已完成） | `error-codes.md` 补工具层错误码表（123/123 全覆盖，经审计脚本校验）——见 `fix/agent-tool-guards` 分支 | 无 |
| P0（已完成） | `scripts/analyze_traces.py` + `scripts/audit_error_codes.py` 两个只读脚本（本分支） | 无 |
| P1（需改动） | 日志/轨迹**只读视图**挂载进容器 | 低（纯新增绑定，走 extraBindings） |
| P2（需改动） | `scripts/` 随 `ContainerInstaller` 释放到容器 + prompts 增加「自查日志」指引 | 低 |
| P3 | 自动「教训 → prompts」 | **高**，须先解决第三节四点 |

**建议**：先做 P1 + P2，让这条链路**可观测、可人工迭代**；观察一段时间、确认模式稳定后，
再评估是否值得做 P3 的自动化。跳过 P1 直接做 P3，等于在看不见数据的情况下改提示词。

## 五、附：本轮发现的问题（属代码层面，不在本方案范围）

`audit_error_codes.py` 检出 **5 组同义分裂**，会让 AI 无法靠码稳定检索：

| 词干 | 分裂写法 | 首现位置 |
| --- | --- | --- |
| `INVALID_ARG` | `BAD_ARG` / `INVALID_ARGS` / `INVALID_ARGUMENT` | VirtualScreenTool:160 / ListFilesTool:56 / BrowserTool:135 |
| `INVALID_ACTION` | `INVALID_ACTION` / `UNKNOWN_ACTION` / `UNSUPPORTED_ACTION` | ManageMcpTool:182 / BrowserTool:412 / MemoryTool:171 |
| `MISSING_ARG` | `MISSING_ARG` / `MISSING_ARGS` | VirtualScreenTool:148 / SearchCodeTool:53 |
| `WRITE_FAILED` | `SAVE_FAILED` / `WRITE_ERROR` / `WRITE_FAILED` | MemoryTool:353 / FileTools:250 / VirtualScreenTool:392 |
| `SEARCH_FAILED` | `SEARCH_ERROR` / `SEARCH_FAILED` / `SEARCH_HTTP_ERROR` | SearchCodeTool:89 / WebSearchTool:115 / WebSearchTool:98 |

建议另立 issue 收敛（保留旧码一个兼容期）。因本轮工单明确要求「不重构错误码为枚举」，
故不在本 PR 内做。**收敛后重跑 `audit_error_codes.py` 即可验证**。
