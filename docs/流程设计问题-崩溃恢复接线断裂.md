# 流程设计问题：崩溃恢复与任务状态的接线断裂

> 目标：审计 AiCode III 的**流程设计**（不是找代码写错），重点看各机制之间的**接线**是否完整。
> 本文件只做设计分析，不含任何代码改动。
> 结论指向一类问题：**机制造得细，但「最后一公里」没接**——部件之间断开，而单个部件单看都是对的。

## 〇、方法与边界

- **分析方法**：不只读单个文件，而是顺着「**谁调用了它 / 谁消费了它的输出**」往下追。这类接线断裂
  单纯读某个文件永远发现不了——每个部件自身都自洽。
- **环境限制**：本环境无法编译、无法运行、无真机。本文全部结论为**源码级**（含双工具交叉验证），
  **不含运行时实测**。凡属推断均已标注。
- **反误报**：每条「缺失」类断言都用 `grep` 与 `rg` 双工具交叉验证（本仓 `rg` 输出存在标识符
  渲染异常——匹配文本被替换成 `n`，故关键结论一律回读原文，不依赖单次搜索结果）。

## 一、结论速览

| # | 严重度 | 问题 | 一句话 |
|---|---|---|---|
| 1 | **高** | 崩溃恢复算出了结果，却只写进日志 | 检测→**无 UI 出口**，用户看不到恢复入口 |
| 2 | **高** | 状态机一半状态是死的 | `WAITING_APPROVAL` 永远进不去，却被列为「可恢复」 |
| 3 | 中 | 「执行中」与「等授权」在账本里不可区分 | 恢复动作完全不同，但系统分辨不出来 |
| 4 | 低 | `prune()` 只在 `finish()` 里调用 | 冷启动产生的 `RECOVERABLE`/`FAILED` 记录永不清理 |
| 5 | 低 | 软收敛提示跨来源不去重 | 同一轮可能同时注入两条意思相近的纠偏提示 |

**共同形状**：问题不在「写得好不好」，在**部件之间的接线**。

## 二、问题详情

### 问题 1（高）崩溃恢复：算出来了，然后扔掉

**设计意图（代码注释白纸黑字）**：

- `CrashRecoveryPlanner`：*"判定为「可恢复」不等于「自动重跑」——只是标记出来**供用户选择继续**。"*
- `DurableTaskRepository.scanForRecovery()` KDoc：*"可恢复 → 置 RECOVERABLE **并返回给调用方提示用户**。"*
- `DurableTaskEntity` KDoc：*"仅标记为可恢复**并提示用户**，避免在用户未预期时自动执行有副作用的工具。"*

三处注释都承诺了「提示用户」。

**实际接线**（`app/src/main/java/com/aicode/feature/agent/presentation/AIAgentViewModel.kt:986-996`）：

```kotlin
// 冷启动崩溃恢复：扫描非终态 durable 任务，可恢复者标记出来（不自动重跑）。
viewModelScope.launch(Dispatchers.IO) {
    runCatchingCancellable { durableTaskRepository.scanForRecovery() }
        .onSuccess { verdicts ->
            val recoverable = verdicts.filterIsInstance<RecoveryVerdict.Recoverable>()
            if (recoverable.isNotEmpty()) {
                FileLogger.i(TAG, "冷启动发现 ${recoverable.size} 个可恢复的长任务（未自动重跑，等待用户继续）")
            }
        }
        .onFailure { FileLogger.w(TAG, "崩溃恢复扫描失败: ${it.message}") }
}
```

**判定结果被读出 → 只写进 `FileLogger` → 丢弃。** 没有 `_state` 更新、没有 Flow 暴露、没有 UI 事件。

**双工具验证**：
- `grep -rn "RecoveryVerdict\|Recoverable" app/src/main`（排除定义与仓库两文件）→ **零命中**
- `grep -rn "可恢复\|崩溃恢复\|恢复任务" app/src/main --include=*.kt` → **零命中**

即：`RecoveryVerdict` 全仓**只有一个消费者**（就是这个把它丢掉的 L988），UI 层**完全没有**「恢复/继续」这个概念。

**后果**：进程被系统杀掉的长任务，会被认真判定为「可恢复」、状态被正确置为 `RECOVERABLE`，
然后**这个结论只存在于一份日志文件里**。用户重启 App 看到的是一片空白，只会觉得「我的任务莫名其妙没了」。

**为什么定高**：这不是缺功能，是**功能做了一半且在骗人**——注释、状态流转、扫描逻辑全都到位，
唯独出口没接。而且它**静默**：没有报错、没有崩溃，只是什么都不发生。

**对比证据（同一段 `init` 里）**：`sessionUseCase.initColdStartCleanup()`（`:983`）是**真接上了**的
（把中断的工具回填为「已中断」并展示）。**同一处代码，一个接了出口、一个没接**——说明不是能力限制。

### 问题 2（高）状态机有一半状态是死的

`TaskStateMachine` 定义了 9 个状态、11 个事件，转移表完整且带穷尽性设计（未在表中的组合返回 `Rejected` 而非抛异常）。**单看这个文件，质量很高。**

但追「**谁在发这些事件**」（双工具交叉验证，排除状态机自身的定义与转移表）：

| 事件 | 实际发出次数 |
|---|---|
| `SUCCEED` / `FAIL` / `CANCEL` | 各 1~2 次 ✅ 有生产者 |
| `START` | **0** |
| `REQUEST_APPROVAL` | **0** |
| `APPROVAL_GRANTED` / `APPROVAL_DENIED` | **0** |
| `PAUSE` / `RESUME` | **0** |
| `CRASH_DETECTED` | **0** |
| `EXHAUST_RETRIES` | **0** |

（唯一的生产者是 `AIAgentViewModel.kt:1662/1683/1695` 的三处 `finish(...)`。）

**直接后果：`WAITING_APPROVAL` 是一个永远无法进入的状态**——而产生它的 `REQUEST_APPROVAL` 事件全仓零发射。

**它偏偏被列进了「可恢复白名单」**（`CrashRecoveryPlanner.kt:36-41`）：

```kotlin
private val IN_PROGRESS_STATES = setOf(
    TaskState.RUNNING,
    TaskState.WAITING_APPROVAL,
    TaskState.PAUSED,
    TaskState.RECOVERABLE,
)
```

**更深的一层：`RECOVERABLE` 也不是走状态机进去的。**

状态机注释说：*"崩溃恢复关键不变量：只有 `RUNNING` 可因 `CRASH_DETECTED` 进入 `RECOVERABLE`。"*
但实际路径是 `DurableTaskRepository.kt:100-101`：

```kotlin
is RecoveryVerdict.Recoverable -> guarded {
    dao.upsert(task.copy(state = TaskState.RECOVERABLE.name, updatedAt = ...))
}
```

**直接改字符串，绕过了 `transition()`，`CRASH_DETECTED` 从未被发出。** 注释描述的那条不变量，实际由另一条路径实现。

**定性**：这不是 bug（现有路径工作正常），而是**防腐层与被保护逻辑脱节**。
读代码的人会认为这 8 个事件是活的、这些转移路径会被走到——**实际上一半的转移表是设计文档，不是运行逻辑。**

### 问题 3（中）「正在执行」与「等授权」在账本里同形

承接问题 2。权限等待的实现（`ToolPermissionManager.kt:30-44`）：

```kotlin
suspend fun awaitApproval(request: PendingToolPermission): PermissionChoice {
    val decision = CompletableDeferred<PermissionChoice>()
    synchronized(lock) { pending[request.id] = Entry(request, decision); publish() }
    try {
        return decision.await()          // 纯内存、无超时
    } finally {
        synchronized(lock) { pending.remove(request.id); publish() }
    }
}
```

**三条已证实的事实**：
1. 等待是**纯内存**的 `CompletableDeferred`，不落库；
2. **没有超时**（全文件无 `withTimeout`）；
3. 待决请求表 `pending` 与两个 `StateFlow` 都只在内存中。

**于是**：用户在权限弹窗上犹豫时进程被杀 → 账本里该任务状态**仍是 `RUNNING`**
（因为 `REQUEST_APPROVAL` 从未发出，state 没变过）→ 冷启动被判定为「**可恢复**」。

**但 `RUNNING` 此刻同时表示两种处境**：
- 真的在执行（被杀后重跑有意义）
- 卡在授权弹窗等用户点（被杀后重跑 = 再弹一次，且**当时要授权什么已经不知道了**）

`DurableTaskEntity` 的字段只有 `promptSnippet` 与 `round`——**没有任何字段记录「当时在等什么授权」**
（已核实：全字段无 `pending`/`approval`/`permission`）。

**所以恢复动作缺少必要上下文**：状态机精心设计了 `WAITING_APPROVAL → RECOVERABLE` 这条路来处理
「等授权时崩溃」，但这条路**永远不会被走到**（问题 2），而它所承载的信息**也从未被持久化**。

**后果**：即便问题 1 接上了 UI，用户点「继续」时系统也无法还原现场——不知道当时在等哪条命令的授权。

### 问题 4（低）`prune()` 只挂在 `finish()` 上

`DurableTaskRepository`：

```kotlin
suspend fun finish(taskId: String, event: TaskEvent) {
    transition(taskId, event)
    prune()                                   // L76：唯一调用点
}
```

全仓 `prune()` 只有这一个调用点（已核实）。

**问题**：以下记录**永远不会被清理**——
- 冷启动扫描出来的任务（`scanForRecovery` 里置 `RECOVERABLE` / `FAILED` 的那批）；
- 置为 `RECOVERABLE` 后**用户一直不处理**的（可能长期悬挂）；
- 任何非经 `finish()` 结束的路径。

`scanForRecovery` 与 `prune` 都是 `suspend`，在冷启动时串一次是显然做法，但没做。
`RETENTION_MS = 7 天` 的设计意图（"防表无限增长"）因此在部分路径上失效。

**严重度低**：表增长缓慢（每用户请求一条），且 `scanForRecovery` 每次冷启动都会命中这些记录。
但设计意图与实际行为不一致，且 `RECOVERABLE` 长期堆积会让恢复扫描的表越来越大。

---

### 问题 5（低）软收敛提示跨来源不去重

`applyLoopGovernance`（`StatefulAgentWorkflow.kt:1474-1516`）把两个治理器的提示追加到工具结果末尾：

- `ToolLoopSentinel` → `SuspectedLoop` → `"检测到重复调用（…），请换用不同思路或参数，不要用相同参数重试。"`
- `FailureCircuitBreaker` → `WarnedOnce` → `"已连续多轮工具调用失败，请先核对失败原因与参数，再决定是否继续。"`

两者判断的都是「你在原地打转」，**同一轮完全可能同时触发**（重复调用且都失败）→ 注入两条意思相近的提示。

**作者已意识到重复**：硬停路径都加了 `if (stopReason == null)` 保护（避免覆盖首个停因）。
**但软提示没有任何跨来源去重**——硬停去重了，软提示没有。

**严重度低**：只是提示文本冗余，不改变流程走向。值得注意的是**不对称**：同一个函数里，
作者对「硬停」做了去重、对「软提示」没做，说明去重是被当作"避免覆盖停因"来处理的，
而未把"提示重复"视为同类问题。

## 三、根因归纳

五个问题共享同一个形状：**机制内部很干净，机制之间的接线缺失。**

- `TurnGovernor` / `ToolLoopSentinel` / `FailureCircuitBreaker` / `TaskStateMachine` /
  `CrashRecoveryPlanner` —— **全部是纯函数、零依赖、可单测**，注释还写明了设计理由。单个文件质量都高。
- 断裂发生在**边界**：谁发事件、谁消费结果、谁清理、谁去重。

**这解释了一个现象**：这套代码读起来很扎实，但实际体验里仍会有「说不清为什么没生效」的地方。
因为问题不在可读性，在**部件之间的箭头**——而箭头是读单个文件时最容易忽略的东西。

**方法论上的教训**：审计流程设计时，读「文件内容」的收益远低于追「调用关系」。
本文 5 条全部来自追问「谁调用了它 / 谁消费了它」，没有一条来自通读某个文件发现"写法有问题"。

## 四、建议的修复方向（按性价比排序）

1. **接上恢复出口**（问题 1）——收益最高、改动最小。
   把 `scanForRecovery` 的结果暴露成 `StateFlow`，在会话列表或首页出一条「上次的任务被中断，是否继续」。
   现有 `RecoveryVerdict.Recoverable` 已带 `taskId`/`sessionId`/`promptSnippet`/`round`，够用。
2. **补授权上下文持久化**（问题 3）——恢复要能还原现场，否则问题 1 修完仍不完整。
   给 `DurableTaskEntity` 加待授权信息，或至少在进入 `awaitApproval` 前发一次 `REQUEST_APPROVAL`。
3. **让状态机成为唯一入口**（问题 2）——`scanForRecovery` 改走 `transition()` 并补发 `CRASH_DETECTED`；
   未使用的事件与状态要么接上，要么标注为「保留设计」以免误读。
4. **冷启动串一次 `prune()`**（问题 4）——一行调用。
5. **软提示去重**（问题 5）——加一个「本轮已注入提示」的标志。

**建议顺序**：1 → 2 → 3。问题 1 单独修就能让用户看到恢复入口；但如实说，
**只修问题 1 而不修问题 3，恢复出来的任务可能带着错误的授权上下文**——两者最好一起做。
