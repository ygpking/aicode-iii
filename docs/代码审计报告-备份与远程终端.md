## 二、缺陷详情

### 缺陷 1（高）provider 密钥备份往返：既不解密也不重加密

**位置**：`app/src/main/java/com/aicode/feature/backup/data/BackupManagerImpl.kt:750-781`（导出）、`:783-814`（导入）

```kotlin
// 导出（L754/L768/L780）：直接透传数据库中的原始密文
private fun AIProviderEntity.toDto() = ProviderDto(
    apiKey = apiKey,
    apiKeys = apiKeys,
    proxyPassword = proxyPassword
)
// 导入（L787/L801/L813）：同样直接透传，未调用 secretVault.encrypt
private fun ProviderDto.toEntity() = AIProviderEntity(
    apiKey = apiKey,
    apiKeys = apiKeys ?: "",
    proxyPassword = proxyPassword ?: ""
)
```

**同一文件内的对照实现**（L816-832）恰恰是正确写法，且注释写明了设计意图：

```kotlin
private fun RemoteConnectionEntity.toDto() = RemoteConnectionDto(
    // 导出为明文（备份跨设备迁移需用新设备密钥重加密），密码与 passphrase 同口径。
    secretVault.decrypt(authData).orEmpty(),          // L819 导出解密
    passphrase?.let { secretVault.decrypt(it) }
)
private fun RemoteConnectionDto.toEntity(): RemoteConnectionEntity? {
    // 导入时按本机密钥重新加密；PRIVATE_KEY 的 authData 是私钥路径，不加密。
    if (authType.equals("PASSWORD", ignoreCase = true)) secretVault.encrypt(authData).orEmpty() else authData,  // L829
    passphrase?.let { secretVault.encrypt(it) }
}
```

**问题链条（四环，每环均已单独核实）**：

1. **导出侧**：`toDto()` 是 `AIProviderEntity` 的扩展函数，作用于 Room 原始行，看到的就是密文。
   `rg "decrypt" BackupManagerImpl.kt` 只命中 L265（备份**容器**解密）与 L819/L820（远程连接），**provider 路径无解密**。
2. **导入侧**：`ProviderDto` 的 `apiKey`/`apiKeys`/`proxyPassword` 在 `BackupSnapshot.kt:142/163` 均为普通
   `String` 透传字段；`restoreMeta`（L600-639）直接 `aiProviderDao.insertAllProviders(meta.providers.map { it.toEntity() })`，
   **全文件搜索无任何导入后重加密补偿步骤**。
3. **覆盖性**：`AIProviderDao.kt:22-23` 为 `@Insert(onConflict = OnConflictStrategy.REPLACE)`，
   导入会**覆盖**目标设备上本来可用的 provider 行。
4. **不可修复性**：密文绑定 AndroidKeyStore 别名 `aicode_secret_vault_v1`，该密钥随卸载销毁且**永不出设备**，
   故导入的密文在新设备上**永远解不开** → `decrypt()` 返回 null → `AIProviderRepositoryImpl.kt:125/151` 的
   `.orEmpty()` 把 provider 静默变成"空 API Key"。
   而 `AIProviderRepositoryImpl.kt:74-81` 的防销毁守卫又会因"既有密文解不开"而 **`return@withTransaction` 拒绝写入**，
   用户**无法通过重新填写来修复**，只能删除并重建 provider。

**触发场景**：设备 A 备份（或任意一次卸载重装/清除数据）→ 设备 B 恢复。该场景正是 L818 注释声明的设计用途。

**为什么不是"备份本就只用于同设备"**：L818 注释明确把"备份跨设备迁移"当作目标场景，且远程连接路径已按此实现——
**是 provider 路径违反了本模块自己写下的契约，而非契约不同**。

**证据等级**：源码（四环均已直接读到代码行）。

### 缺陷 2（高）远程后台命令退出码恒为 0，失败被上报为成功

**位置**：`app/src/main/java/com/aicode/feature/terminal/domain/RemoteTerminalSessionManager.kt:128`、`:263`

```kotlin
if (command != null) {
    val init = command + (if (notify) "" else "; exec /bin/sh")   // L128：notify=true 时什么都不追加
    termSession.write(init + "\n")
}
...
target.runState = RunState.Finished(0)                            // L263：硬编码 0
...
TabFinishedEvent(target.id, target.title, target.command, 0, ...) // L270：同样硬编码 0
```

**本地版对照**（`TerminalSessionManager.kt:213-216`）——本地版是**刻意**做了退出码捕获的，注释还写明了原因：

```kotlin
// notify=true：echo 后 `exit $ec` 让 shell 以命令真实退出码结束 → proot 透传 → 回调 exitStatus 正确
// notify=false：echo 后 `exec ${shell}` 保活，标签可复用
val afterCommand = if (notify) "; exit \$ec" else "; exec ${containerEngine.defaultShell()}"
val shellCommand = "cd ~/workspace 2>/dev/null; export ENV=/etc/profile; " +
    "$command; ec=\$?; echo \"[command exited: \$ec]\"$afterCommand"
```

远程版**两样都没有**：没有 `ec=$?` 捕获，也没有 `exit $ec` 收尾。
`rg "command exited|ec=\$|exit \$ec|extractExitCode|monitorBackgroundExit"` 在远程版**零命中**（实测）。

**后果（源码可证）**：`AIAgentViewModel.kt:1228`
```kotlin
outcome = if (exitCode == 0) NotificationOutcome.COMPLETED else NotificationOutcome.FAILED,
```
远程命令即使失败也恒为 `exitCode == 0` → 上报 **COMPLETED**。即"远端构建失败"会被模型当作
"已完成"继续往下走——**静默的错误结果**，比报错更危险。

**关键：那句"远程无退出码"的注释是错的，且被本仓代码直接证伪。**

`RemoteTerminalSessionManager.kt:261` 与 `SshShellBackend.kt:21-23` 都写着
"remote shells have no meaningful exit status, so 0 is returned"。但是**同一个代码库**里：

```kotlin
// app/src/main/java/com/aicode/feature/agent/domain/container/RemoteSshEngine.kt:94-105
// 与同步路径一致：sshj 的 exitStatus 在流 EOF 后未必就绪，close 后才保证有值；
// 否则 channel 未同步时会拿到 null，调用方把正常结束的命令误判为失败。
runCatching { session.close() }
val exitCode = session.exitStatus          // ← 真实退出码，可拿到
...
emit(CommandEvent.Exit(exitCode))
```

即：**sshj 0.38.0 确实能提供退出码，`RemoteSshEngine` 已经在用，且注释还写明了"必须先 close 再读"这个坑。**
`SshShellBackend.waitForExit()` 目前是 `shell.join(); return 0`——它把可用的信息主动丢掉了。
因此这不是"平台限制"，而是**远程终端路径复制本地逻辑时漏掉了退出码捕获，并用一句不成立的注释固化了该疏漏**。

**触发场景**：REMOTE_SSH 模式下 `terminal` 工具以 `notify=true` 启动 `pnpm test`（`notify=true` 的文档用途即"后台任务完成后通知 AI"）。
测试失败 → 本地版会报 `Finished(1)` 并通知；远程版**通知内容为"成功"。**

**证据等级**：源码 + 同仓反证（`RemoteSshEngine.kt` 存在可用写法）。
**未闭合项**：`notify=true` 时远程 shell 不退出、`onSessionFinished` 是否触发，需真机 SSH 才能确认——
若确认不触发，则问题进一步恶化为"AI 永远等不到通知"；若触发，则至少是"失败报成功"。**两种情况下 L263/L270 的硬编码 0 都成立。**

### 缺陷 3（中）远程后台命令无唤醒锁、无前台服务

**位置**：`RemoteTerminalSessionManager.kt:83-93`（`startBackgroundCommand`）

本地版同方法（`TerminalSessionManager.kt:236-237`）有两行保活：
```kotlin
startKeepaliveService()
backgroundLeases[id] = lifecycleSupervisor.acquireLease("terminal:$id")
```
远程版**两行都没有**：`rg "startKeepaliveService|acquireLease|lifecycleSupervisor|backgroundLeases"` 零命中（实测）。

`RuntimeLifecycleSupervisor` 的注释正描述了这一后果："终端后台任务只起了前台服务却没拿锁，锁屏后 CPU 挂起、构建中断"。

**为什么远程也需要**：SSH 通道与 `TerminalSession` 都在**本进程**内。进程被冻结则不再读取通道，
退出码观测（缺陷 2 修复后）与输出收集都无法进行——远端服务器在跑，客户端却观察不到。

**证据等级**：源码（缺失已实测确认）；"锁屏必然中断"为推断，未真机验证。

### 缺陷 4（中）工作区路径未转义即拼入单引号 shell 命令

**位置**：`RemoteTerminalSessionManager.kt:125`

```kotlin
termSession.write("cd ~/workspace 2>/dev/null || cd '${wsPath.trimEnd('/')}' 2>/dev/null\n")
```

`wsPath` 仅用单引号包裹，**未做转义**。路径含单引号时引号提前闭合，剩余部分变成 shell 语法。

本仓已有现成且被复用的转义函数，共 **5 处**定义（实测）：`WorkspaceRepository.kt:495`、
`RemoteSshEngine.kt:262`、`RemoteSshConnection.kt:277`、`GitRepository.kt:771`、`ShellArgs.kt:148`。
`RemoteTerminalSessionManager.kt:7` **已经 import 了 `WorkspaceRepository`**（实测），却未使用其 `shellQuote`。

**触发场景**：工作区路径含撇号（如 `.../o'brien-project`）→ `cd '/data/.../o'brien-project'` 被解析为
引号串 `/data/.../o` 加裸词 `brien-project` → `cd` 失败报语法错。注意 `||` 回退分支是**同一个坏字符串**，救不了。
由于该 `cd` 在命令写入（L129）之前，后续命令会在**错误的工作目录**下执行。

**定性**：作为**正确性缺陷**上报（`shellQuote` 同仓存在却未用）。**不作为安全漏洞上报**——
利用它需要攻击者控制工作区路径，在本地应用上不成立。

**证据等级**：源码（转义缺失与 helper 存在均已实测）。

### 缺陷 5（低）凭据 `save` 与 `parse` 校验不一致（当前不可达）

**位置**：`FileCredentialRepository.kt:52`（校验）vs `:90`（丢弃）

```kotlin
// save：只校验 host
if (host.isEmpty()) return@withLock
// parse：username 为空则整行丢弃
if (host.isEmpty() || username.isEmpty()) null
```

理论上存在"写入成功但读回消失"的往返数据丢失。**但当前不可达**：三个调用点均有非空校验——
`CredentialEditorScreen.kt:62` 的 `canSave`、`CredentialPromptDialog.kt:53` 的 `canSave`
（含 `username.trim().isNotBlank() && token.isNotBlank()`）、`LegacyCredentialMigrator.kt:53`。
`rg` 确认无绕过 UI 的第四方调用点。

**故降级为"防御纵深不一致"**，建议在 `save` 内补同款校验以消除该形状，**但不声称存在可复现的数据丢失**。

**证据等级**：源码。可达性判定为源码级结论（未运行）。

## 三、已证伪 —— 请勿重复调查

以下候选经反向核实**不成立**，记录在此以免后续重复投入：

1. **`FileCredentialRepository` 明文存储 token 是缺陷** → **不是缺陷**。
   文件位于应用私有目录 `filesDir/aicode/git-credentials`，且它必须保持 git `credential.helper=store`
   的标准格式，因为**容器内的 git 会直接读取该文件**（类头注释与 `AIEditorApp.kt` 注释均说明"UI 与 git 共用同一份"）。
   加密它会使容器 git 失效。这是**有约束支撑的设计选择**，不是疏漏。
2. **`SqlScriptSplitter` 分块错误** → **证伪**。以忠实 JS 移植跑了约 10 个边界用例
   （`CREATE...;INSERT...;`、行注释、块注释含分号、`SELECT ';';`、空输入、仅注释、`';';` 等），
   全部与预期一致，无错误切分。
3. **`MigrationLoader.loadMigrations` 未按版本排序是缺陷** → **不是缺陷**。
   Room 按 `startVersion` 索引迁移，且实际迁移版本为 **8..57 连续无重复**，项目自带的
   `scripts/check_migrations.py` 实测通过：`[OK] 迁移版本号对账通过 — 本地迁移版本 8..57，共 50 个`。
4. **`BackupCrypto` 分块加密会丢字节** → **证伪**。对 `pending` 预读字节做了重点复现：
   明文长度为 CHUNK 整数倍（4/8/12）与任意余数（5/9）、空输入，全部字节数守恒；
   实测"块 1 首字节 = 5（期望 5）"，证明预读字节被正确搬运而非丢弃。`index++` 位于 `break` 之前，末块序不影响读取侧对齐。
5. **`BackupViewModel` 把口令存成 `String`**（`WorkspaceSelection.password`，`:31-35`/`:107`）
   而其余路径刻意用可清零的 `CharArray` → 确为不一致，但 `cancelImportSelection`/`reset()` 会立即解引用，
   泄漏窗口被限制在对话框打开期间，**属加固建议而非可复现缺陷**，不计入缺陷清单。
6. **`GitViewModel.kt:619` 用 `"${hash}^"` 取根提交父节点** → 最初判断"根提交 diff 坏了"是**错的**：
   `showFileContent` 在非零退出时返回 `""`，恰好得到"整文件新增"的**正确**渲染。
   仅残留一个更窄的问题（所有非零退出都塌缩成"空旧侧"，真读取失败也会被显示成全部新增而非报错），
   **不足以列为缺陷**，记为设计模糊点。
