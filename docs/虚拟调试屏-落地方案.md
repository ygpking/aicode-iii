# 虚拟调试屏 · 落地方案

> 前置阅读：`docs/虚拟显示器可行性验证.md`（原始实测证据、命令与踩坑记录）。
> 本文只讲**怎么落地**，事实依据均可回溯到该文档。

> ## ⚠ 实现期修正（务必先读，已推翻本文部分原始设计）
>
> 本文最初把宿主定在 **Shizuku UserService**（Kotlin 同源码）。实现期**实测证伪**，已改为
> **`app_process` + 裸 dex** 守护进程。以下为修正结论，与下文冲突处以后者为准：
>
> | 原设计 | 实测结果 | 现行方案 |
> | --- | --- | --- |
> | UserService 内建虚拟屏 | UserService 进程**不是合法应用进程**，拿不到可用 `Context`；而 `createVirtualDisplay` 必传 Context 且包名要与 uid 匹配 → 不可行 | `app_process` 拉起，`ActivityThread.systemMain()` 取 systemContext，再 `createPackageContext("com.android.shell")` |
> | 控制链用 AIDL | Shizuku `runCommand` 是**一次性**调用，无法向长驻进程喂 stdin | **localhost socket**：daemon 监听 `127.0.0.1`，每次 `printf 'CMD\n' \| toybox nc 127.0.0.1 <port>`。host 与 client 同为 shell(2000)，**避开跨 uid SELinux** |
> | dex 从 app 私有目录取 | `/data/user/0/<pkg>/files` 对 shell **完全不可读**（SELinux `app_data_file`） | dex 随 APK 打包在 `assets/`，由 shell `unzip -p` 抽到 `/data/data/com.android.shell/files/`（`/data/app/**/base.apk` 为 0644，shell 可读） |
> | — | 仅靠进程退出**不会**销毁虚拟屏（孤儿屏 `state=OFF` 残留） | 必须持有 `VirtualDisplay` 引用并显式 `release()` |
> | — | 非守护 `HandlerThread`/`Looper` 使 JVM 不退出，进程残留 | 退出前 `System.exit(0)` |
> | — | daemon 若为普通子进程，父 exec 返回后即被收走 | `setsid nohup ... &` 脱离会话（实测跨独立调用 PING 通） |
>
> **已实测通过**：uid 2000（免 root）下 `OPEN→LAUNCH→CLOSE→EXIT` 全流程；显示器数回到 1、
> 任务残留 0、进程 0、端口释放、物理屏不受影响。`displayId` **动态分配（实测见 2/3/4/5）**，
> 集成时必须使用 `OPEN` 的返回值，**不可硬编码**。
>
> 现行文件：`vdsupport/src/com/aicode/vdscreen/VirtualScreenHost.java`（宿主）、
> `app/src/main/assets/virtualscreen/host.dex`（产物）、
> `app/src/main/java/com/aicode/feature/virtualscreen/`（集成层）。

## 一、目标

让 AI 在**一块独立于物理屏的虚拟显示器**里打开并操作 App：

| 需求 | 验收标准 |
| --- | --- |
| 用户无感 | 物理屏不出现浮层、不被抢焦点、分辨率/亮度不变 |
| 不靠截图 | 通过无障碍节点树读界面、执行操作 |
| 隔离 | AI 的操作不污染用户当前的 App 与数据 |
| 可回收 | 用完彻底移除，不留任务残留 |

**明确的非目标**（v1 不做）：

- 不做像素级截图/录屏（盲操作不需要；虚拟屏截图走 ImageReader 需另设通道）。
- 不做多用户 / Work Profile 隔离（数据层共享同一 `/data/data`，见可行性文档第八节）。
- 不替代 `ShizukuTool` 的通用 shell 能力——本方案是其上的专用通道。

## 二、总体架构

### 2.1 为什么必须是三个部分

三件事**分属不同权限域**，无法合并：

| 能力 | 谁能做 | 为什么不能合并 |
| --- | --- | --- |
| 创建虚拟屏 | shell(2000) / root(0) | App 进程无 `CREATE_VIRTUAL_DISPLAY` |
| 读节点树 | **已安装 APK** 内的 `AccessibilityService` | 系统只把 a11y 能力授给真实应用；`app_process` 自注册 `UiAutomation` 会被 SIGKILL |
| 编排 / UI | AiCode 普通 App 进程 | 对用户负责的入口 |

### 2.2 组件图

```
┌──────────────────────────── AiCode 主进程 ────────────────────────────┐
│  VirtualScreenController            （编排：分配 displayId、派活、清理）│
│  VirtualScreenTool                  （暴露给 Agent 的工具）            │
│  VirtualScreenHostManager           （投递 dex、拉起 daemon、发指令）   │
└───────┬──────────────────────────────────────────┬───────────────────┘
        │ ①socket: OPEN/LAUNCH/CLOSE/LIST/PING   │ ②同 App 跨进程
        ▼                                        ▼
┌──────────────────────┐            ┌────────────────────────────────────┐
│ vdshost daemon       │            │ :vdscreen 进程                      │
│ app_process / uid2000│            │ VirtualScreenA11yService            │
│ VirtualScreenHost    │            │  - getWindowsOnAllDisplays()        │
│  - ImageReader 作    │            │  - performAction / dispatchGesture  │
│    BufferQueue       │            │  - 向 Controller 回报节点树/结果     │
│  - createVirtualDisplay           └────────────────────────────────────┘
│  - setsid 保活      │
└──────────────────────┘
```

三条链路职责（**以修正后的实现为准**）：

- ① **控制链**：主进程 → `app_process` daemon（**socket**）。只传指令与 `displayId`，不传 Surface。
- ② **感知/操作链**：主进程 ↔ `:vdscreen` 进程内的 a11y 服务。**同 App、跨进程**，用 Binder/Messenger。
- ③ **保活链**：daemon 自身 `setsid` 脱离会话（跨 exec 调用存活）+ App 侧前台服务保活。

### 2.3 关键点：Surface 不跨进程

`createVirtualDisplay` 的接收端 Surface **必须在持有它的进程内创建**。
所以 `ImageReader` 建在 UserService 进程里，对外只暴露 `displayId`。
若将来要做像素通道，也从该进程取帧（可行性文档已证实 `screencap -d` 读不到）。

## 三、组件详设

### 3.1 VirtualDisplayHost（shell/root 侧）

**职责**：虚拟屏的创建、保活、销毁。

**身份**：由 Shizuku 以 **shell(uid 2000)** 或 **root(uid 0)** 实例化。

**易错点（实测确认）**：`Context` 的包名**必须与调用 uid 匹配**，否则
`createVirtualDisplay` 抛 `SecurityException: packageName must match the calling uid`。

```kotlin
// ✅ 正确：uid 2000 用 com.android.shell 的 context
val ctx = systemContext.createPackageContext("com.android.shell", 0)
```

| uid | 可用 context |
| --- | --- |
| 2000 (shell) | `createPackageContext("com.android.shell")` |
| 0 (root) | `systemContext` 或 `com.android.shell` 均可 |

**创建参数**（实测值）：

```kotlin
val flags = 0x1        // VIRTUAL_DISPLAY_FLAG_PUBLIC
          or 0x8       // VIRTUAL_DISPLAY_FLAG_OWN_CONTENT_ONLY   不镜像物理屏
          or 0x100     // VIRTUAL_DISPLAY_FLAG_DESTROY_CONTENT_ON_REMOVAL
val config = VirtualDisplayConfig.Builder("aicode-vd", 1080, 2400, 440)
    .setFlags(flags)
    .setSurface(imageReader.surface)          // 必须给 Surface，否则 state=OFF
    .setDefaultBrightness(1.0f)
    .build()
```

**AIDL 接口草案**：

```aidl
interface IVirtualScreenHost {
    int create(int width, int height, int dpi, int flags);  // 返回 displayId，失败抛异常
    void release(int displayId);
    boolean isAlive(int displayId);
}
```

**语言选择**：Kotlin 即可（Shizuku UserService 与本服务同源码，不必再走 dex + `app_process` 那条路）。
可行性文档里的 dex 方案是**验证手段**；工程化后用 UserService 更省事。

> ⚠️ **待验证（#1 实现期风险）**：Shizuku `UserService` 的 attach 路径与 `app_process` 不同。
> 可行性文档验证的是 `app_process`。落地第一步必须确认 UserService 内能否同样成功创建虚拟屏
> （预期可行：同为 shell/root + 可用 `createPackageContext`，但**未实测**）。
> 若不可行，降级为「随 App 打包一份 dex，由 Shizuku 用 `app_process` 拉起独立守护进程」。

### 3.2 VirtualScreenA11yService（App 侧）

**声明**（`app/src/main/AndroidManifest.xml`）：

```xml
<service
    android:name=".feature.virtualscreen.domain.a11y.VirtualScreenA11yService"
    android:exported="true"
    android:process=":vdscreen"
    android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">
    <intent-filter>
        <action android:name="android.accessibilityservice.AccessibilityService" />
    </intent-filter>
    <meta-data android:name="android.accessibilityservice"
               android:resource="@xml/virtual_screen_a11y" />
</service>
```

`app/src/main/res/xml/virtual_screen_a11y.xml`：

```xml
<accessibility-service xmlns:android="http://schemas.android.com/apk/res/android"
    android:accessibilityEventTypes="typeAllMask"
    android:accessibilityFeedbackType="feedbackGeneric"
    android:accessibilityFlags="flagDefault|flagRetrieveInteractiveWindows|flagIncludeNotImportantViews"
    android:canRetrieveWindowContent="true"
    android:canPerformGestures="true"
    android:notificationTimeout="100"
    android:description="@string/virtual_screen_a11y_desc" />
```

`flagRetrieveInteractiveWindows` 是 `getWindows*()` 可用的**前提**。

**核心 API**：

```kotlin
// 关键：必须用「所有显示器」版本。单数 getWindows() 只给当前活跃屏，看不到虚拟屏。
val all: SparseArray<List<AccessibilityWindowInfo>> = getWindowsOnAllDisplays()
val windows = all.get(targetDisplayId) ?: return   // 按 displayId 取
val root = windows.firstOrNull()?.root              // 节点树根
```

**操作原语**：

| 动作 | 实现 | 备注 |
| --- | --- | --- |
| 点击 | 找可点击祖先 → `performAction(ACTION_CLICK)` | 文本节点常 `clickable=false`，**必须上溯找祖先**（实测 WLAN 的 text 节点不可点，祖先 `LinearLayout` 可点） |
| 输入文本 | `ACTION_SET_TEXT` 或 `ACTION_FOCUS` + 发送 | 需 `Bundle` 传 `ACTION_ARGUMENT_SET_TEXT_CHARSEQUENCE` |
| 滑动 | `dispatchGesture()` | 需 `canPerformGestures` |
| 返回/主页 | `performGlobalAction(GLOBAL_ACTION_BACK/HOME)` | 作用于**当前活跃屏**，多屏下语义待验证 |

**不要用 `input -d <displayId>`**：实测对虚拟屏完全无效
（窗口 `NOT_FOCUSABLE`、`touch NONE`、无输入视口）。盲操作走 `performAction`，
直接作用于节点，绕过 InputFlinger。

**进程隔离的必要性**：a11y 服务放 `:vdscreen` 而非主进程，原因：
① 主进程被系统回收/冻结时，屏上操作不中断；
② 与主进程解耦，便于单独重启。

### 3.3 VirtualScreenController（编排层）

**职责**：对上层提供「一次会话」的完整语义。

```kotlin
interface VirtualScreenController {
    suspend fun open(request: VirtualScreenRequest): Result<VirtualScreenSession>
    suspend fun close(session: VirtualScreenSession)
}

data class VirtualScreenRequest(
    val packageName: String,       // 要调试的 App
    val width: Int = 1080,
    val height: Int = 2400,
    val dpi: Int = 440
)

data class VirtualScreenSession(
    val displayId: Int,
    val packageName: String,
    val taskId: Int?,              // 用于清理
)
```

**`open()` 步骤**（顺序敏感）：

1. 校验 Shizuku 已授权（复用 `ShizukuManager.state`）
2. 校验无障碍服务已启用（读 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 或本地状态）
3. `host.create(...)` → `displayId`
4. `cmd package resolve-activity --brief <pkg>` 解析 launcher activity（**不要写死 activity 名**）
5. `am start --display <displayId> -n <activity>` 投屏
6. `input -d <displayId> keyevent 224`（WAKEUP）—— 虚拟屏初始可能 `isSleeping`
7. 轮询 `getWindowsOnAllDisplays()[displayId]` 直到窗口就绪（超时兜底）

**`close()` 步骤**（顺序敏感，**不可颠倒**）：

1. **先 `am force-stop <packageName>`** ← 关键，否则任务会「搬家」到主屏污染 Recent
2. `host.release(displayId)`
3. 清理 `VirtualScreenSession` 状态

```
⚠️ 为什么必须先 force-stop：
   DESTROY_CONTENT_ON_REMOVAL 只销毁「窗口内容」，不删 Activity 任务记录。
   实测漏做此步 → 物理屏 Recent 里冒出 6 条残留任务。
   补做后 → 残留 0 条。
```

### 3.4 VirtualScreenTool（暴露给 Agent）

参照现有 `ShizukuTool` 的形态（`feature/agent/domain/tool/shizuku/ShizukuTool.kt`）：

| 工具方法 | 语义 |
| --- | --- |
| `virtual_screen_open(packageName)` | 开一块屏并启动目标 App |
| `virtual_screen_close()` | 关闭并清理 |
| `virtual_screen_dump()` | 返回当前节点树（结构化文本，供模型阅读） |
| `virtual_screen_click(text \| id \| bounds)` | 定位并点击 |
| `virtual_screen_input(text)` | 输入文本 |

**节点树转文本**要给模型做裁剪（参照 `EventTrace` 的「去噪」教训）：

- 保留：`className` / `text` / `contentDescription` / `viewIdResourceName` / `bounds` / `clickable` / `editable`
- 丢弃：不可见节点、纯布局容器（`ViewGroup` 无文本无 id 无 click）、重复祖先链
- 加**节点序号**，让模型用序号引用，避免它复述坐标

## 四、关键设计决策与取舍

| 决策 | 选择 | 理由 | 备选/代价 |
| --- | --- | --- | --- |
| 虚拟屏创建者 | Shizuku UserService | 复用既有 Shizuku 架构，无新依赖 | `app_process` + dex：更独立但要自带 dex 与 IPC |
| a11y 服务位置 | `:vdscreen` 独立进程 | 与主进程解耦、更耐冻 | 主进程内：省 IPC，但一起被回收 |
| 节点读取 API | `getWindowsOnAllDisplays()` | **唯一**能看到非活跃屏的入口 | `getWindows()` 只给当前屏（实测） |
| 操作方式 | `performAction` | 绕过 InputFlinger，多屏下可靠 | `input -d`：实测无效 |
| 隔离级别 | 同包名（同一 App 实例） | 零改造 | 改包名副本：数据独立但需重打包 |
| 权限要求 | **Shizuku（adb 或 root 均可）** | 免 root 已实测成立 | 无 Shizuku 则不可用（需明确降级提示） |

**权限结论（重要）**：早前文档写「`app_process` 跑在 system uid(1000)」是**错的**。
实测：与 Shizuku 授权方式一致 —— root 则 `uid=0`，adb 则 `uid=2000`，**两者都能建屏**。
真正门槛是 **context 包名与 uid 匹配**（见 3.1）。

### 5.2 dex 的构建（已自动化）

**dex 不签入仓库**，由 `app/build.gradle.kts` 的 `buildVdHostDex` 任务在 `preBuild` 阶段生成：

```
:app:preBuild → :app:buildVdHostDex  （Exec bash scripts/build-vd-host.sh）
                                    ↓ javac -source/-target 8 -bootclasspath android.jar
                                    ↓ d8 --min-api 30  → 裸 dex
              app/build/generated/vdHost/virtualscreen/host.dex
                                    ↓ 经 vdHostGeneratedDir 并进 assets
              APK: assets/virtualscreen/host.dex
```

单独跑（改完 host 源码想快速校验时）：

```bash
bash scripts/build-vd-host.sh /root/sdk-arm64 /tmp/vdout   # SDK 目录 + 输出目录都得传
./gradlew :app:buildVdHostDex --rerun
```

几处刻意选择：

- **dex 不入库**：签入产物就必然出现「改了源码忘了重生 dex」，且这种不一致在 APK 里
  完全静默。改为构建期生成后，该风险在结构上归零。
- **绕开 `JavaCompile`**：宿主要的是「裸 dex、只依赖 android.jar、min-api 与 App 无关」（跑在
  `app_process` 里、不在 App 进程）。套 `JavaCompile` 得额外压制 Kotlin/核心库脱糖/SDK 版本
  一堆与它无关的设定，用脚本更直白。
- **assets 逐 flavor 各挂一次**：flavor 的 sourceSet **不继承** main 的 assets 源目录，只挂 main 会漏。
- **`d8` 的输出目录必须先建**（它不自己创建，否则报 `Invalid output: ...`）。
- **`inputs`/`outputs` 都声明了**：增量构建下只有 `VirtualScreenHost.java` 真变才重编。

## 六、权限与用户授权

| 权限 | 获取方式 | 用户可见性 |
| --- | --- | --- |
| Shizuku（root 或 adb） | 复用 `ShizukuManager.requestPermission()` | 首次弹窗 |
| 无障碍服务 | **系统设置里手动开启** | 设置页显示「AiCode」——需明示用途 |

**无障碍服务无法默认开启**（除 root/Shizuku 静默写 secure settings，但那会绕过用户知情，
不建议作为默认路径）。落地实现：设置页「软件权限」页内的**虚拟屏分组**给出**状态自检 + 一键跳转**，
未开启时明确告知「只能开不能操作」。

实现要点（见 `feature/virtualscreen/presentation/`）：

- `VirtualScreenViewModel` 三态区分：**已连接** / **已开启但未连接** / **未开启**。
  第三种与第一种不能混——只看 `isRunning` 会把「刚勾选、系统还异步绑定」误报成「没开启」，
  让用户反复去开关。故另读 `ENABLED_ACCESSIBILITY_SERVICES` 判断是否已在列表中。
- `VirtualScreenSection` 提供：无障碍状态 + 一键跳系统无障碍页、重新体检、daemon 状态、
  以及**残留会话回收**（上一轮被中断时会留屏）。
- 跳转只用标准 `ACTION_ACCESSIBILITY_SETTINGS`，**不依赖 Settings 的包内私有 extra**
  （AOSP 的 `EXTRA_COMPONENT_NAME` 非公开 API，跨 ROM 不保证）——代价只是用户需在列表里翻找一次。

**合规提示**：无障碍服务能读取全系统界面内容，须在设置页写清用途边界，
且**不采集非虚拟屏的窗口内容**（代码层面限制只读目标 `displayId`）。

## 七、生命周期与清理

```
开启 → 创建虚拟屏 → 投 App → 操作… → 关闭
                                        ├─ force-stop 目标 App     ← 必须
                                        ├─ release 虚拟屏
                                        └─ 复原 session 状态
```

**必须处理的异常路径**：

| 场景 | 处理 |
| --- | --- |
| Shizuku 掉线 | 屏随之销毁；提示用户，清理 session |
| App 被系统回收 | 屏随 UserService 绑定解除而销毁；重启后不自动恢复 |
| 无障碍被用户关闭 | 感知链中断；保留屏但拒绝操作，提示 |
| 进程崩溃 | 启动时做**孤儿屏检测**：扫 `dumpsys display` 有无 `aicode-vd`，有则清理 |

**孤儿屏检测**（防脏读）是必须项：进程被杀时 `release` 不会执行，
会留下一块无主虚拟屏。启动时按屏名 `aicode-vd` 扫描并回收。

## 十一、已知坑清单（实现时直接查）

1. **`createVirtualDisplay` 报 `packageName must match the calling uid`**
   → 用 `createPackageContext("com.android.shell")`。
2. **屏 `state=OFF`、Activity 落不进去** → 少传 Surface；必须给 `ImageReader.surface`。
3. **`getWindows()` 看不到虚拟屏** → 必须 `getWindowsOnAllDisplays()`。
4. **`input -d <id>` 无反应** → 虚拟屏非焦点屏，属预期；改用 `performAction`。
5. **移除虚拟屏后物理屏冒出 App** → 移除前必须 `am force-stop`。
6. **`am task remove` 不存在** → 只能用 force-stop。
7. **文本节点不可点击** → 上溯找 `clickable` 祖先。
8. **`Looper.prepare()` 缺失** → `ActivityThread.systemMain()` 抛
   `Can't create handler inside thread that has not called Looper.prepare()`。
9. **MIUI 冻结进程** → `do_freezer_trap` 下 `Handler.postDelayed` 不执行；a11y 逻辑写事件回调里。
10. **`pm install -r` 不重启已绑定的 a11y 服务** → 跑的还是旧代码；改代码后必须
    `am force-stop` 再重绑。
11. **改 `enabled_accessibility_services` 会重绑** → 移出再写回可强制刷新；多个服务用 `:` 分隔。
12. **`sed -n "/Display #N/,/Display #0/p"` 越界** → 当 `Display #0` 排在 `#N` 之前时范围会吃到 EOF；
    用 `awk` 按行号切片。
13. **容器→设备传文件** → 容器起 `python3 -m http.server`，设备用 `curl`（设备无 wget）。
14. **`CLASSPATH` 指向签名 APK 会 `Aborted`** → 崩溃在 `AndroidRuntime::startReg → FindClass`。
    必须给**裸 dex**（现已随 APK assets 打包，由 `unzip -p` 抽出）。
15. **`nohup ... &` 不够，daemon 会被收走** → 父 exec 返回后子进程被一并清理；
    必须 `setsid nohup ... &` 且 stdin 重定向 `< /dev/null`。
16. **daemon 不能靠 stdin 触发服务模式** → detached 后 stdin 立即 EOF，主循环立刻结束、进程退出；
    改为命令行 `--server <port>` 直接进服务模式。
17. **`displayId` 不是固定值**（实测 2/3/4/5 递增）→ 必须用 `OPEN` 返回的 id；硬编码会 `CLOSE` 到不存在的屏。
18. **`/data/user/0/<pkg>/files` 对 shell 不可读** → 连父目录 `stat` 都 `Permission denied`（SELinux `app_data_file`）；
    dex 改走 APK assets + `unzip -p`。
19. **toybox `netstat -l` 不生效**（`-tln` 仍列出全部连接）→ 判“端口是否释放”不能看有无 LISTEN 字样，
    应看目标端口是否出现 `LISTEN` 状态；客户端侧 `TIME_WAIT` 堆积是正常的。
20. **`dumpsys SurfaceFlinger --display-id` 的 `Display N` 序号不等于 `displayId`** →
    该输出里的编号是另一套序列，判显示器数量用 `grep -c`（1=仅物理屏）即可，不要拿它当 displayId。
21. **构建需 `ANDROID_HOME`** → 未设时 `SDK location not found`；
    `ANDROID_HOME=/root/sdk-arm64 sh gradlew :app:assembleUniversalDebug`（`./gradlew` 无执行位）。
22. **`unzip -p` 的条名要带 `assets/` 前缀** → APK 内是 `assets/virtualscreen/host.dex`，
    写成 `virtualscreen/host.dex` 会**静默抽出 0 字节**（不报错），随后 `app_process` 报 `Aborted`。
    注意：Android `AssetManager.open()` 用**无前缀**路径，`unzip` 用**带前缀**路径，两者不能混用。
23. **Kotlin 每个类只能有一个 `companion object`** → 「顶部放常量 + 底部放单例」的写法会直接编译失败
    （`Only one companion object is allowed per class`）。合并为一个，用 `private const` 控制可见性。
24. **a11y 静态实例的 setter 可见性** → `companion object` 内的 `var x: T? = null; private set`
    会让**同类外部**的 `onServiceConnected` 也写不了；应用 `internal set`（同模块可写、跨模块只读）。
25. **`dispatchGesture` 没有 displayId 参数——不设就打到物理屏（已修）**
    `GestureDescription.Builder.mDisplayId` 默认是 `Display.DEFAULT_DISPLAY`（=0，已查 AOSP 源码），
    目标屏由 `Builder.setDisplayId()` 写进 `GestureDescription`，AIDL 侧 `dispatchGesture(..., int displayId)`
    就从它取。后果不只是「滑不动虚拟屏」，而是**在用户屏幕上注入手势**（坐标还是虚拟屏的），
    直接破坏「不影响用手机」这个根本承诺。必须 `.setDisplayId(displayId)`（API 30+）。
    另注：三参重载 `dispatchGesture(gesture, callback, handler)` 是 `final`、无版本重载，无需版本分发。
26. **公共虚拟屏在设备锁屏时被锁屏盖住（已修）**
    实测：`mWakefulness=Dozing` 时，新建的公共虚拟屏上 `com.android.systemui` 的
    `ty=KEYGUARD_DIALOG` 压住目标 App（`visibleRequested=false`），a11y 只读到锁屏的 **8 个节点**
    （`miui_keyguard`/`current_time`），根本进不了 App。加 flags `OWN_DISPLAY_GROUP (1<<11) |
    ALWAYS_UNLOCKED (1<<12)`（即 `0x1|0x8|0x100|0x800|0x1000 = 6409`）后，
    **锁屏状态下仍读到 110 个真实节点并可用**。两个都是 `@hide` 常量，需硬编码。
    `ALWAYS_UNLOCKED` 只在「非默认 display group」的屏上生效，故必须一起传；
    需 `ADD_ALWAYS_UNLOCKED_DISPLAY` 权限（实测 `com.android.shell` 持持有）。
    而「用户锁屏时 AI 干活」正是本功能最有价值的场景，不能不处理。
27. **重装/`force-stop` 后 MIUI 会掉掉 a11y 启用项**
    实测：重装 APK 或 `am force-stop` 应用后，`settings get secure enabled_accessibility_services`
    里本服务消失（只剩 SCENE）。生产环境需实现「检测到未启用时引导用户重新开启」，
    这正是待补的设置页入口要解决的。

## 十二、待决问题（需产品决策）

1. **是否需要像素通道？** 盲操作不需要；若要做「可视化回放」，需从 ImageReader 取帧
   （`screencap -d` 读不到虚拟屏）。成本较高。
2. **虚拟屏分辨率/密度**：固定 1080x2400@440 还是跟随物理屏？跟随需动态读取。
3. **会话是否持久化**：App 退后台后自动关闭，还是保活（需前台服务 + 常驻通知）？
4. **是否允许 AI 操作非虚拟屏的界面**？本方案限定在目标 `displayId`，建议保持限定。
