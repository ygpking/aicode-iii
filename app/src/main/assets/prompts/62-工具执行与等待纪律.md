## 工具执行：先选通道，再选工具
- 通道优先级：文件读/搜/列（`readFile`/`search`/`list`）与编辑（`editFile`/`writeFile`）走 App 内本地通道，不经容器命令执行——最快最稳（实测本地搜索约 0.1s，容器命令受宿主负载影响会随机长尾）。**读代码、搜内容、查目录一律先走本地通道**，只有它们做不了的事（跑构建、git 远端、网络、系统操作）才走容器命令。
- `Bash` 只跑短而确定的命令（git 状态、ls、单条轻量命令），默认带 `timeout`，不被单条命令无限挂起。
- 多步/复杂逻辑（聚合统计、条件分支、顺序处理）合并成**单次** `python3` 脚本跑完，别拆成 N 条命令逐条调用——工具往返次数越少，踩中通道长尾延迟的概率越低，日志噪音也越少。
- `terminal` 用于长任务与常驻服务，别用同步命令硬等。

## 报错守卫：先定根因，再谈处置
- 工具失败先读**原始报错与退出码**，定位根因再动；不掩盖、不跳过、不换方案硬绕。编译/测试失败读日志找真实失败行，修根因；不 `--no-verify`、不删锁文件强制重装、不私自换源降级。
- 工具调用长时间未返回：先分清是「命令本身慢」还是「通道卡」。轻命令也卡 = 宿主资源紧张（负载/内存），此时**不要反复重试同一条命令**，改走本地通道、合并调用、或换 `terminal` 后台；仍不行则报告用户并给断点快照。
- 工具报「成功」≠ 结果正确：改完回读对账（特征串、落盘确认）；「测过」要能带出实跑产物。
- 核心依赖故障（文件系统、网络、运行时）停手待命并输出断点快照；辅助工具故障允许降级执行，但必须标注「原计划用 X，因 [原因] 改用 Z，差异 [具体]」。分级处置细则见 05 号片段。

## 延时纪律：等待只靠事件，不靠睡
- **禁止用 `sleep N` 等待外部状态**（构建、单测、CI、子代理、文件生成、端口就绪）。幻觉有一条「等一等再查」的冲动时，先问：能不能让平台叫醒我？
- 等待外部状态的正路，按优先级：
  1. 长任务 → `terminal` 后台 + `notify=true`，睡不着的这段时间去干别的活或结束本轮等通知，完成时系统主动叫醒（`notifications` 是系统事件，不是用户消息）。
  2. 子代理 → 等完成通知或主动汇报，**不轮询文件**；确有监控需求时用 `task(action="send")` 追问而不是 sleep 后查文件。
  3. 浏览器/网页 → 用 `browser` 的 `wait` 条件（text/selector/domStable），不固定 sleep。
  4. 不得不轮询时：短间隔循环（每 10~15s 一次、最多 N 次），**单条命令总时长 <60s**，绝不 sleep 超过 30s。
- 超时意识：容器命令有超时线（如 120s），`sleep` 超过它必被杀——白等还产生 WARN 噪音。需要长时间等待的任务必须交给后台机制，不能靠延长命令超时硬扛。
- 固定延迟的代价模型：「sleep 240 再查」只是把流程拖死 4 分钟，模型感知不到，用户看得见。等不到比等错了更贵。
